# Design

## Context

Проект пустой: есть только спека Foreca Weather API (`foreca-weather-api.openapi.json`) и правила OpenSpec. Всё, что ниже, опирается на измерения, выполненные на машине разработки (Node 22.20, FFmpeg 7.1.5, MediaMTX 1.21.3 в Docker, Debian), а не на предположения — это принципиально, потому что несколько очевидных решений оказались нерабочими.

Ключевые факты, полученные экспериментально и влияющие на архитектуру:

- `@hey-api/openapi-ts@0.99` **падает без установленного `typescript`** (`Cannot read properties of undefined (reading 'AnyKeyword')`).
- В спеке нет ни одного `required` в ответах и есть дубли `operationId`: 37 операций на 24 уникальных идентификатора. Без нормализации генератор создаёт `zGetDaily`, `zGetDaily2` … `zGetDaily6`, и вторая операция называется так же, как первая.
- `@napi-rs/canvas` течёт в двух местах, и обе утечки измерены:
  - ветка 1.x: `canvas.data()` даёт около 1.4 МБ на кадр, `global.gc()` не помогает (309 → 1592 МБ за 1000 кадров);
  - **ветка 0.1.x начиная с 0.1.89**: сама отрисовка даёт около 8 КБ на кадр при неизменной куче и внешней памяти, `clearAllCache()` не помогает. Граница регрессии найдена по версиям: 0.1.88 — 0.36 КБ/кадр, 0.1.89 — 8.6 КБ/кадр, 0.1.100 — 8.4 КБ/кадр.
  - Итог: зафиксирована **0.1.88**. На ней 18 000 кадров дают рост RSS около 3 МБ.
- `-tune stillimage` при публикации по RTSP стабильно роняет FFmpeg через ~12 секунд (`Broken pipe`, код 224); с `-tune zerolatency` процесс живёт нормально.
- MediaMTX не принимает одновременно `alwaysAvailableFile` и `alwaysAvailableTracks` — падает при старте с `cannot be used together`.
- Живой поток появляется не мгновенно: от старта FFmpeg до доступного кадра прошло около 5 секунд (набор пробы входа).
- `alwaysAvailable` с offline-файлом работает: при полностью отсутствующем паблишере путь отдаёт валидный H.264/1 fps; читатель переживает смерть паблишера и его повторный запуск, не отключаясь (проверено на 640x480, затем заглушка пересоздана под D1).

## Goals / Non-Goals

**Goals:**

- Один процесс Node, который детерминированно превращает ответ Foreca в непрерывный RTSP-поток D1 704x576.
- Два URL на один поток без второго кодирования.
- Вещание не прекращается ни при сбое Foreca, ни при падении FFmpeg, ни при рестарте сервиса.
- Соблюдение требований Foreca к атрибуции на кадре.
- Конфигурация, пригодная и для интерактивного запуска, и для контейнера.

**Non-Goals:**

- Второй поток и второе кодирование (FullHD, отдельный sub-stream с другим содержимым).
- ONVIF-обнаружение и эмуляция камеры: NVR подключается по custom RTSP URL.
- Аутентификация RTSP-читателей.
- Звуковая дорожка.
- Мультиканальность и несколько локаций в одном процессе.
- Интерактивная настройка вида (тема, набор элементов) — макет фиксирован.
- Использование официальных SVG-символов Foreca: они доступны только через My API, поэтому иконки рисуются собственные.

## Decisions

### Источник данных: 3-hourly, а не daily

`/api/v1/forecast/3hourly/{location}` даёт внутридневную динамику и уже содержит признак дня/ночи в коде символа, а также параметр `tz`. Дневной эндпоинт описывает только окно 07:00–18:00, не имеет `tz` и не позволяет нарисовать референсную кривую.

`periods` запрашивается с запасом (не менее 60 шагов), после чего данные **обрезаются по времени**, а не по индексу: нужны ровно семь суток от ближайшего шага. Обрезка по индексу дала бы сдвиг на границе суток.

Альтернатива — `hourly`: даёт больше точек и более гладкую кривую, но это 168 шагов на неделю вместо 56, больший ответ и более шумный график на 640 пикселях. Отклонено.

### Типы: нормализация спеки + генерация

Пайплайн кодогенерации:

```
foreca-weather-api.openapi.json
        |
        | scripts/normalize-openapi.ts  (переписать operationId = method + path)
        v
build/foreca.normalized.json
        |
        | @hey-api/openapi-ts (плагины typescript + zod)
        v
src/generated/{types.gen.ts, zod.gen.ts, index.ts}   (коммитятся)
```

Причины нормализации: без неё `tsc --strict` падает на дублирующихся идентификаторах, а zod-схемы получают имена вида `zGetDaily3`, не привязанные к пути. После нормализации имена становятся вида `zGetApiV1ForecastDailyLocationResponse` и `tsc` проходит чисто.

Плагин zod, а не ручные type guards: спека не содержит `required`, поэтому все поля в схемах необязательные. Валидатор на границе обязателен, но он проверяет структуру, а не полноту. Полнота проверяется отдельным шагом доменной сборки: шаг прогноза без `time` или `temperature` отбрасывается, а если после отбраковки шагов не осталось — ответ считается неуспешным.

**Спека врёт про `nullable`.** Из 554 необязательных скалярных полей `nullable` объявлен только у 15, а API регулярно возвращает `null`: например `adminArea2: null` в поиске локаций. Прямая генерация давала схему, которая отвергала валидный ответ, и мастер настройки не мог сохранить даже правильный токен. Поэтому нормализация спеки помечает все необязательные скалярные поля как `nullable` (539 полей) — правило узкое, массивы и объекты не трогаются. Сгенерированные типы после этого содержат `T | null`, и транспортный слой обязан приводить `null` к `undefined`, чтобы наружу не протекал `null`.

Генерат коммитится, потому что сборка и запуск не должны зависеть от сети и от версии генератора. Версия `@hey-api/openapi-ts` и `zod` фиксируется точно; обновление — отдельная задача с проверкой диффа.

### Доменная модель отделена от схемы API

Сгенерированные типы описывают транспорт, а не то, что рисуется. Между ними — явный шаг сборки, который:

1. парсит ответ zod-схемой;
2. нормализует время в часовой пояс локации;
3. группирует шаги по календарным датам локации;
4. отбрасывает шаги без обязательных полей;
5. вычисляет производные величины (сумма осадков за 6 часов, минимум/максимум дня, направление стрелки ветра);
6. помечает модель признаком устаревания и временем обновления.

Такой шаг тестируется на сохранённых ответах Foreca без сети. Это единственное место, где «сырые» данные превращаются в домен, поэтому остальной код не знает про особенности Foreca.

### Рендер: canvas 0.1.x + raw RGBA

Выбран `@napi-rs/canvas` **ветки 0.1.x** (точная версия фиксируется) из-за утечки в 1.x. Альтернативы:

| вариант | почему нет |
|---|---|
| `sharp` | нет нормальной работы с текстом и вёрсткой, а весь кадр — это подписи |
| `resvg-js` | каждый кадр требует SVG→PNG, дороже без выгоды при 1 fps |
| чистый JS-растр | текст, шрифты и сглаживание пришлось бы писать вручную |

Кадр собирается в RGBA и передаётся в FFmpeg через `pipe:0`. PNG в рантайме не используется. Замеры для 640x480 (до перехода на D1): полная отрисовка ~0.04 мс, `data()` ~0.19 мс, PNG-энкод ~9.5 мс. При 1 fps разница между raw и PNG по CPU несущественна (Node 0.2% против 1.1%), но raw не требует ни энкодера, ни декодера в FFmpeg и не создаёт промежуточных буферов.

`data()` возвращает новый `Buffer` на каждый вызов, поэтому рендерер **переиспользует один `Uint8Array`**, а не `data()`, если это возможно без изменения API; иначе кадр уходит в FFmpeg сразу и не удерживается.

### Кадр: единый макет D1 704x576

Раз макет один, второй поток — это тот же кадр, а не уменьшенная копия. Поэтому нет ни `scale`, ни второго кодировщика. Компоновка:

```
+----------------------------------------------------------+
| Погода в <локация>                    обновлено ДД.ММ ЧЧ:ММ |
| ПРОГНОЗ НА НЕДЕЛЮ          [УСТАРЕЛО — заметный бейдж]    |
|   сб     вс     пн     вт     ср     чт     пт           |
|  ДД.ММ  ...                                              |
|  иконки: 4 на день + подписи часов                     |
|  график: сетка, ноль, сглаженная кривая, точки min/max    |
|  осадки: столбики за 6 ч + подписи                        |
|  ветер: стрелка + скорость по дням                        |
|                                          [лого Foreca]    |
+----------------------------------------------------------+
```

Сглаживание — Catmull-Rom, ограниченный диапазоном соседних значений, чтобы кривая не выходила за пределы данных. Цвет кривой меняется по знаку температуры: на пересечении нуля вставляется точка ровно на нулевой линии, поэтому смена цвета происходит в месте перехода, а не между шагами данных. Точки экстремумов ставятся на час реального минимума и максимума (а не по центру дня) и подписываются значением — на этом разрешении место для подписи есть, а читать цифры с самой кривой неудобно.

Базовое разрешение макета — **704x576 (D1)**: его поддерживает большинство аппаратных регистраторов. Другие размеры получаются масштабированием координат и шрифтов от высоты кадра, а не отдельной вёрсткой: одна раскладка обслуживает несколько разрешений, и порядок областей сохраняется. Нижняя граница размера шрифта зафиксирована в 8 px — ниже текст после сжатия H.264 не читается.

Отдельно решено **не рисовать живые часы**: при 1 fps они бесполезны, а время обновления данных — полезно и заодно служит индикатором свежести.

Про иконки: часы не фиксированы. Сетка шагов Foreca привязана к моменту запроса, и на реальном запуске пришли часы 20/23/02/05, а не 03/09/15/21. Поиск по фиксированным часам не находил совпадений, срабатывал запасной вариант «показать все», и на 640 px восемь иконок налезали друг на друга. Поэтому шаги дня делятся на четыре равные группы и из каждой берётся представитель — это работает при любой сетке и проверено тестом на сдвинутой сетке.

### Транспорт: один энкод, две ссылки через прокси

```
Node (canvas, 1 fps)
      | RGBA 704x576
      v
   FFmpeg (libx264)  --- RTSP/TCP --->  MediaMTX path "weather"
                                            |  alwaysAvailable + offline_vga.mp4
                                            |
                                    path "weather_sub": source=rtsp://.../weather
                                            |
                                rtsp://host:8554/weather
                                rtsp://host:8554/weather_sub
```

Рассматривались три варианта второго URL:

| вариант | итог |
|---|---|
| tee-муксер, две публикации | работает, но требует объявления обоих путей в конфиге MediaMTX; при отсутствии пути публикация падает с 400, а при `onfail=ignore` молча теряет одну ветку |
| второй процесс FFmpeg с `-c copy` из первого | лишний процесс и лишняя точка отказа |
| `source: redirect` | **отклонён после проверки на регистраторе**: отдаёт `302` с `Location`, а MediaMTX строит его из внутреннего адреса (`127.0.0.1:8554`), поэтому NVR пошёл бы на собственный localhost. Кроме того, аппаратные регистраторы, как правило, не следуют RTSP-редиректам и показывают канал неактивным |
| **pull-прокси (`source: rtsp://...`)** | выбран: оба пути отвечают `200 OK` и отдают один и тот же поток, без второго кодирования |

Про UDP: сервер принимает и TCP, и UDP. TCP остаётся основным, но часть регистраторов запрашивает только UDP и без него получает `461 Unsupported Transport` — это наблюдалось на реальном устройстве (Dahua), поэтому UDP включён намеренно, а не «на всякий случай».

Параметры кодирования (проверены на живом потоке):

```
-f rawvideo -pix_fmt rgba -s 704x576 -r 1 -i pipe:0
-c:v libx264 -preset veryfast -tune zerolatency
-profile:v main -level 3.1 -pix_fmt yuv420p
-bf 0 -g 1
-x264-params nal-hrd=cbr:force-cfr=1:repeat-headers=1
-b:v 400k -minrate 400k -maxrate 400k -bufsize 800k
-f rtsp -rtsp_transport tcp <url>
```

Обоснование каждого решения:

- `zerolatency`, а не `stillimage` — измеренное падение паблишера.
- `-g 1` — при 1 fps ключевой кадр на каждом кадре; NVR подключается мгновенно и не считает поток мёртвым из-за отсутствия движения.
- `repeat-headers=1` — SPS/PPS в каждом ключевом кадре, иначе позднее подключение не декодируется.
- CBR (`nal-hrd=cbr`) — статичный кадр в VBR ужимается до 14–21 кбит/с; измерено, что при CBR 400k реальный поток держит 400–430 кбит/с. Предсказуемость важнее экономии: NVR и архив ориентируются на номинальный битрейт.
- `-bf 0` — без B-кадров, чтобы не добавлять задержку и не усложнять совместимость.
- `level 3.1` — достаточен для D1 704x576 и максимально совместим.

### Отказоустойчивость: три независимых слоя

| слой | отказ | поведение |
|---|---|---|
| данные | Foreca недоступна | последний успешный прогноз + бейдж «устарело» |
| данные | нет кэша и нет сети | кадр «нет данных» + логотип, поток идёт |
| кодировщик | FFmpeg упал | MediaMTX играет offline-заглушку, супервизор перезапускает с backoff |
| сервис | Node упал | внешний супервизор (systemd/docker restart) |
| сервер | MediaMTX упал | внешний супервизор, NVR переподключается |

Offline-заглушка генерируется тем же FFmpeg с теми же профилем, уровнем и форматом пикселей, что и живой поток, иначе при переключении читатель перестраивает декодер. Она статична, поэтому весит около 17 КБ.

Коварство заглушки в том, что она скрывает отказ: канал выглядит рабочим, и оператор не замечает, что прогноз давно не обновляется. Поэтому слой «сервис» обязателен, а не рекомендателен: проверено на практике, что без него сервис, запущенный вручную, после падения не поднимается и канал сутки показывает заглушку.

Падение сервиса из-за кодировщика — отдельный сценарий, который супервизор FFmpeg не ловит. Когда FFmpeg умирает, запись в `child.stdin` даёт `EPIPE`; эта ошибка приходит событием `'error'` на поток, а не исключением из `write()`, поэтому `try/catch` вокруг записи её не перехватывает, и `uncaughtException` убивает весь процесс вместе с супервизором. Лечение: обработчик `'error'` на stdin, после которого `write` возвращает отказ, а перезапуск делает тот же супервизор, что и при обычном падении. Дополнительно сервис слушает `close` (при ошибке запуска `exit` не приходит) и сам корректно завершается по `uncaughtException`/`unhandledRejection` с аварийным таймаутом, чтобы внешний супервизор увидел ненулевой код, а не зависший процесс.

### Конфигурация: файл + мастер + env

Приоритет источников: аргументы командной строки → переменные окружения → файл конфигурации → мастер.

Мастер проверяет токен поиском заведомо существующего города (`/api/v1/location/search/{query}`) до сохранения, потому что сохранить неверный токен и узнать об этом только через 30 минут — плохой сценарий. Поиск локации идёт тем же запросом; при нескольких различных результатах мастер показывает варианты с регионом и страной, так как «Караганда» может найтись не одна. Повторяющиеся записи (одинаковый идентификатор) схлопываются: на реальном запуске Foreca вернула две неразличимые Караганды, и выбор между ними был бессмысленным.

Токен дополнительно проверяется на символы, допустимые в HTTP-заголовке. Без этого не-ASCII токен ломал заголовок, запрос падал сетевой ошибкой, и пользователь искал проблему не там.

Запись атомарна (временный файл + `rename`), права `0600`. В репозитории лежит `config.example.json` без секретов, реальный файл — в `.gitignore`.

После успешной настройки сервис сразу начинает вещание: первый запуск не должен заканчиваться сообщением «конфигурация сохранена» и тишиной.

### Наблюдаемость и отладка

- `/health` отдаёт состояние: активна ли публикация, когда был последний успешный кадр, сколько было перезапусков, возраст данных, состояние последней ошибки Foreca.
- `/snapshot.png` отдаёт текущий кадр — без него проверка вёрстки возможна только через NVR.
- `scripts/check-stream.sh` проверяет готовность потока для регистратора: публикацию, RTSP, профиль, уровень, формат пикселей, служебные заголовки, ключевой кадр, UDP и код ответа второй ссылки. Это первое, что нужно запустить, если NVR не показывает канал.
- `/metrics` в формате Prometheus опционален, но структурно заложен.

## Risks / Trade-offs

- **Зависимость от конкретной версии canvas.** `@napi-rs/canvas@0.1.88` — не последняя версия: 0.1.89 и новее течёт на отрисовке, 1.x течёт на `data()`. → Точная фиксация версии, тест на стабильность RSS (тысячи кадров), отдельная задача на перепроверку при выходе новых версий: сначала замер, потом обновление.
- **Нет `required` в спеке Foreca.** Типы честно говорят «поле может отсутствовать», поэтому нельзя полагаться на типы для обязательных для рендера полей. → Явный шаг валидации домена с отбраковкой неполных шагов и тестами на реальных ответах.
- **Дубли `operationId` в спеке.** Прямая генерация даёт неоднозначные имена и падение `tsc`. → Скрипт нормализации в пайплайне, проверка в CI, что после нормализации `tsc --noEmit` проходит.
- **1 fps может не устраивать часть регистраторов.** Некоторые NVR считают поток «мёртвым» при отсутствии движения. → Ключевой кадр на каждом кадре, CBR, при необходимости поднять частоту до 2–5 fps без изменения архитектуры (измерено: 5 fps стоит около 2.3% ядра FFmpeg на 640x480).
- **Одна локация на процесс.** Мультиканальность потребует отдельного процесса или общего планировщика. → Осознанно вне рамок; модель канала изолирована, чтобы расширение не потребовало переписывания рендера.
- **Квоты Foreca.** При 30-минутном обновлении и двух запросах на цикл — около 96 запросов в сутки против лимита 2000. → Запас большой, но при 429 сервис обязан уважать `Retry-After`, а не долбить повторно.
- **Сглаживание может визуально «сгладить» резкий фронт.** Catmull-Rom с ограничением уменьшает, но не устраняет этот эффект. → Ограничение диапазоном соседних значений; при спорных случаях приоритет у фактических точек (они отмечены).
- **Логотип требует свободного поля.** Компоновка под него зарезервирована, иначе придётся переверстывать кадр. → Место под логотип и его поля зафиксировано в макете с самого начала.
- **Собственные иконки вместо официальных.** Официальные SVG доступны только через My API. → Рисуем свои по разбору кода; при появлении доступа замена иконок не затрагивает остальной код.
- **Разные часовые пояса.** Подписи дней считаются в поясе локации, а «обновлено» — тоже; если сервер в другом поясе, это не влияет на кадр. → Часовой пояс локации хранится в модели, а не берётся из системы.
